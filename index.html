Every service quietly accumulates dependencies — a queue, a managed database, four vendor APIs, a cloud role. Nobody wrote them down, and the list only matters on the day one of them breaks. Reachmap writes it down for you, from the manifests you already have.

Why map dependencies

Four questions that are hard today

None of these need a new tool to ask. They need an answer you can trust without a week of archaeology, and one that is still true next month.

When something breaks, know who is in it

A vendor degrades or a region wobbles. Today that starts with a war room and a lot of grep. With a map it starts with a list of exactly which services touch the thing that broke.

“Which services call Stripe?”

Catch the dependency nobody reviewed

New third-party APIs arrive one pull request at a time, each too small to argue about. Nobody decides to depend on eleven vendors; it just happens.

“What did this branch just add?”

What leaves the cluster, which workloads are in PCI scope, and which cloud roles each service assumes. Asked once a year, and it costs a week each time.

The same graph, drawn

Colours carry the node kind, and they are the colours the terminal prints — learn them once here and the scan output reads itself.

[cloud]A named cloud resource — an RDS instance, a queue, a bucket
[external]A third-party API outside your estate
[identity]A cloud role or service account the workload assumes
[opaque]A dependency that exists but whose target is in a Secret
[service]Another service inside the cluster
Why a grep would not do

Most of what a service reaches is written down somewhere other than its container environment. Not hard to find — invisible.

Four of Reachmap's detectors exist for exactly this reason.

01 keda-trigger

The queue nobody can see

A worker that only consumes from SQS has no inbound Service, no ingress and no endpoint in its own environment. The queue lives in the autoscaler's configuration, so without reading KEDA triggers that workload looks like it depends on nothing at all.

02 proxy-sidecar

The database behind localhost

A workload behind a Cloud SQL proxy sees localhost:5432, which every correct scanner suppresses as loopback. The real instance is named only in the sidecar's arguments, as project:region:instance.

03 secret-ref

The connection string in a Secret

A workload mounting orders-db-creds is an unresolved blind spot. When an ACK, Crossplane or Config Connector resource in the same scan names that Secret, Reachmap resolves it to the actual RDS instance — without ever reading the Secret.

04 workload-identity

The role a workload assumes

IRSA, GKE Workload Identity and their Azure equivalent are declared workload→cloud edges sitting in the manifest. The landscape survey found no vendor documenting them, and they are what an IAM-policy expansion needs first.

How it works

Read, resolve, emit

No agent and no cluster required. A directory of rendered YAML is enough; a live cluster is an option, not a prerequisite.

And it tells you how sure it is

An edge you disagree with has to be arguable, so confidence is a bucket with a rule behind it rather than a number. “0.73” is not an argument.

Install

One binary, one vendored dependency

And what it cannot do

A tool that overclaims here loses trust the first time it is wrong.

Secrets

A connection string in a Secret is invisible unless something in the scan describes that Secret. Reachmap does not read Secrets, in cluster mode either.

Constructed endpoints

os.getenv("REGION") + ".internal.foo.com" cannot be resolved statically. Source-code scanning catches some of it later.

Unrendered templates

Refused with a message rather than scanned, because analysing them produces dependencies on literal {{ .Values.host }} strings.

Permitted ≠ observed

Mesh and network-policy edges say a workload may reach something. Proving that it does needs runtime data.
