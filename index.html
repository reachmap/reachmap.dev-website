Every service quietly accumulates dependencies — a queue, a managed database, four vendor APIs, a cloud role. Nobody wrote them down, and the list only matters on the day one of them breaks. Reachmap writes it down for you, from the manifests you already have.

Why map dependencies

Four questions that are hard today

None of these need a new tool to ask. They need an answer you can trust without a week of archaeology, and an answer that is still true next month.

When something breaks, know who is in it

A vendor degrades or a region wobbles. Today that starts with a war room and a lot of grep. With a map it starts with a list of exactly which services touch the thing that broke.

“Which services call Stripe?”

Catch the dependency nobody reviewed

New third-party APIs arrive one pull request at a time, each too small to argue about. Nobody decides to depend on eleven vendors; it just happens. A diff on every PR makes each one a decision.

“What did this branch just add?”

Answer the audit question in minutes

What leaves the cluster, which workloads are in PCI scope, and which cloud roles does each service assume. These questions get asked once a year and cost a week each time.

“What is in scope, and says who?”

See what a move would actually cost

Changing region, account or provider is priced by what is pinned to the old one. A PVC tied to one availability zone and a hardcoded regional endpoint are the same surprise, six months apart.

“What is pinned to us-east-1?”

Why a grep would not do

A pod spec is not the dependency list

Most of what a service reaches is written down somewhere other than its container environment. Four of Reachmap's detectors exist because those dependencies are otherwise invisible — not hard to find, invisible.

keda-trigger

The queue nobody can see

A worker that only consumes from SQS has no inbound Service, no ingress and no endpoint in its own environment. The queue lives in the autoscaler's configuration. Without reading KEDA triggers, that workload looks like it depends on nothing.

proxy-sidecar

The database behind localhost

A workload behind a Cloud SQL proxy sees localhost:5432, which every correct scanner suppresses as loopback. The real instance is named only in the sidecar's arguments, as project:region:instance.

secret-ref

The connection string in a Secret

A workload mounting orders-db-creds is an unresolved blind spot. When an ACK, Crossplane or Config Connector resource in the same scan names that Secret, Reachmap resolves it to the actual RDS instance — without ever reading the Secret.

workload-identity

The role a workload assumes

IRSA, GKE Workload Identity and their Azure equivalent are declared workload→cloud edges sitting in the manifest. The landscape survey found no vendor documenting them. They are also what an IAM-policy expansion needs first.

How it works

Read, resolve, emit

No agent and no cluster required. A directory of rendered YAML is enough; a live cluster is an option, not a prerequisite.

And it tells you how sure it is

An edge you disagree with has to be arguable, so confidence is a bucket with a rule behind it rather than a number. “0.73” is not an argument.

In CI

Every new dependency becomes a decision

Scanning is useful once. Diffing is useful every day. Reachmap compares the graph on a branch against the graph on main and comments on the pull request when a change adds something — failing the build only if you ask it to.

Removals never fail

Every gate fires only on added dependencies. Dropping one is cleanup, and a tool that fails CI for it would punish exactly the change teams should be making.

Findings get their own exit code

0 clean, 1 tool error, 2 usage, 3 findings. Collapsing findings into 1 makes a crash indistinguishable from a tripped gate, and those need different responses at 3am.

Output CI already reads

A markdown comment for the pull request, SARIF for the security tab, Graphviz DOT and Backstage catalog entities for everything downstream.

Install

One binary, one vendored dependency

Go with a single vendored dependency — a YAML parser — so it builds offline, audits in an afternoon and ships as one static binary.

build from source 
$ git clone https://github.com/reachmap/reachmap.dev
$ cd reachmap.dev
$ go build -mod=vendor -o reachmap ./cmd/reachmap
$ ./reachmap scan ./manifests
A note on go install. The module path is reachmap.dev, which needs that domain to serve a go-import meta tag before go install reachmap.dev/cmd/reachmap@latest can resolve. The tag is already in this site's HTML, so it starts working the moment the domain points here. Until then, build from source.
Known limits

Stated plainly

A tool that overclaims here loses trust the first time it is wrong.

  • Secrets. A connection string in a Secret is invisible unless something in the scan describes that Secret. Reachmap does not read Secrets, in cluster mode either.
  • Dynamically constructed endpoints. os.getenv("REGION") + ".internal.foo.com" cannot be resolved statically.
  • Unrendered templates. Refused with a message rather than scanned, because analysing them produces dependencies on literal {{ .Values.host }} strings.
  • Permitted reach is not observed reach. Mesh and network-policy edges say a workload may reach something. Proving it does needs runtime data.
